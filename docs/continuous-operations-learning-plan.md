## 1. 建立現況基準與本次遠端 CI

**預計投入：1～1.5 小時。**

學習重點：區分本機 commit、遠端提交、合併提交與 CI 驗證版本；歷史成功證據不能自動代表目前版本。

- [x] 核對 Git HEAD、遠端分支、PR／merge SHA 與 CI run，確認交付提交是否已 push，以及其遠端檢查結果。
- [x] 建立計畫時本機 HEAD 為 `94b8af8`，訊息為合併 PR #18；因此「尚未 push」需重新查證，不能直接沿用先前摘要。後續確認原交付已合併且 main CI 成功。
- [x] 若提交尚未推送，檢查 diff 與敏感資訊後推送；若已合併，記錄實際驗證 SHA 與 CI run URL。文件更新也核對相對連結。
- [x] 保存最新發布月份、各 DAG 暫停／執行狀態、Pool slot、Lambda digest、Cloud Run revision／digest 與部署開關現況。

**驗收：**交付版本與遠端 CI 可一一對應；若 workflow 未觸發，記錄原因並取得適用的檢查結果，不以舊 run 代替。

## 2. 逐批補齊積欠月份

**預計投入：3～5 小時，另加來源等待及批次執行時間。**

學習重點：來源可用性、冪等載入、revision／checksum、品質發布邊界，以及回填與月排程的分工。

- [x] 先查正式發布狀態，從第一個缺月開始。若現況仍止於 202504，起點為 202505。
- [x] 以執行當下的完整月份與兩類來源實際可用性決定終點。2026-10-02 的上一完整月是 202609，但不能假設已可取得完整來源。
- [x] 建立月份清單：已發布、可回填、來源未就緒、失敗待處理；缺月不得偽裝成零值或完成。
- [x] 依[回填手冊](day16-backfill-manual.md)，每批最多三個連續完整月份，由舊到新處理；來源未就緒時縮小批次。回填期間 monthly 保持暫停，手動入口也遵守單 writer。
- [x] 每月查驗兩類 S3 原檔／manifest／checksum、raw grain／金額、attest、dbt、quality audit 與正式發布版本。PASS／WARN 依既有 gate 判定，FAIL 不發布。
- [ ] 發生中斷先查 job／audit，續跑原 DAG run；未知交易結果不得盲目新增 run。已發布月份依原 run ID 安全重跑。
- [x] 核對 Dashboard 日期邊界與快取，必要時更新既有 runtime 設定，確認新發布月份可見。

**驗收：**截至約定的來源可用終點，沒有未解釋缺月；每月均有發布或未就緒原因，正式 grain 無重複，UI 與查詢一致。保存逐月證據，不只保存 DAG 綠燈。

## 3. 恢復 monthly 排程

**預計投入：1.5～2 小時，真實排程另候觀察。**

學習重點：排程時間、data interval、`catchup=False` 與有限窗口的差異；unpause 不等於補完歷史資料。

- [x] 確認 backfill 已結束、無其他 writer，檢查 DAG import errors、身分有效性、單 slot Pool 與容器健康。
- [x] 核對目前排程為 Asia/Taipei 每月 1 日 00：00，monthly 最多查看最近三期；更舊缺月仍由 backfill 處理。
- [x] 依[排程手冊](day15-operations-manual.md)執行受控檢查，確認已發布月份略過、來源未就緒的行為，以及失敗不發布。
- [x] 條件齊備後解除 monthly 暫停，保存時間、下一次排程與基準版本，觀察 scheduler 實際建立 run。
- [ ] 如出現未知寫入狀態、重複 grain 或品質 FAIL，先暫停排程、保留證據並處理根因，再恢復。

**驗收：**至少一次由 scheduler 建立的真實 run 有可追溯結果。若因來源未就緒而略過，只能證明排程有運作；持續觀察至可用月份自動發布成功。手動 `dags test` 不代替此項。

## 4. 驗證持續運行與復原

**預計投入：2～3 小時設定／演練，另加 2～4 週初步觀察。**

學習重點：應用重試、容器重啟、主機可用性與身分有效期，是不同的故障層級。

- [x] 明定本機運行條件：主機供電與休眠設定、Docker 啟動、網路、AWS／GCP 身分、磁碟與日誌管理；指定維護者與檢查頻率。
- [x] 既有 Compose 已包含 restart policy 與 healthcheck，先驗證實際效果，不把重新加入設定當作完成。
- [x] 在無正式寫入時進行容器／服務重啟演練，確認 metadata 保留、scheduler／worker 恢復及無重複發布；主機重啟測試另外記錄。
- [ ] 記錄服務中斷、run 成敗、資料新鮮度、告警與復原時間。依現有通知限制區分 SNS action 與本人實收。
- [ ] 若本機無法提供所需可用性，提出常駐主機或雲端執行環境的成本／維運比較，另開遷移範圍；本計畫不預設實作雲端 Airflow。

**驗收：**觀察期間與中斷明確可查，至少一次重啟復原通過，且完成一次真實月排程的自動發布。2～4 週可能沒有涵蓋月排程，必要時延長；短期觀察不宣稱全年穩定。

## 5. 啟用並驗證 AWS 自動部署

**預計投入：1.5～2.5 小時。**

學習重點：push 觸發條件、OIDC trust subject、分支限制、image digest 與同一 saved plan 的驗證鏈。

- [x] 核對 `.github/workflows/deploy-aws.yml` 的 push branch／paths、`AWS_DEPLOY_REF`、OIDC subject 與實際部署分支。
- [x] 基準 workflow 的 push branch 為 `feature/ci-oidc-deployment`，而驗收紀錄記載受限 main subject；查明目前配置後統一部署目標，不能只打開開關。
- [x] 本計畫建議的工作分支不必取得正式部署權限；變更依專案流程合入受信任部署分支，維持精確 OIDC 限制。
- [x] 確認 CI 通過、image-only plan guard、序列化部署與舊 digest 回復方式，再設定 `AWS_AUTO_DEPLOY_ENABLED=true`。
- [x] 使用必要且符合 path filter 的實際變更驗證 push 部署，記錄 SHA → workflow → ECR digest → Terraform apply → Lambda digest → 無 drift。
- [ ] 失敗時依既有手冊關閉開關、保存證據並回復舊 digest；服務版本回復不撤銷資料發布。

**驗收：**一次符合條件的 push 自動完成 CI 與部署，digest 一致、無 drift，且保留可用的回復版本。純文件提交不在目前部署 path filter 內，不能用它證明部署開關失效。

## 6. 核對費用並整理資源

**預計投入：1.5～2.5 小時，另加帳單與通知等待；補數前先盤點，持續運行後再核對。**

學習重點：預算通知與費用硬上限不同；服務、儲存、映像與日誌要分開盤點。

- [x] 建立 AWS／GCP 資源清單與補數前費用基準，記錄幣別、帳期、實際／預估費用與稅額範圍。
- [ ] 核對補數期間及常態期間的帳單明細，辨認 BigQuery、Cloud Run、映像儲存、S3、ECR 與日誌等實際費用來源。
- [ ] 查驗 TWD 250 月預算的設定、收件與觸發狀態；區分測試通知與真實門檻通知。尚未達門檻就保留待驗，不刻意花費以觸發。
- [x] 盤點 Cloud Run revisions、Artifact Registry／ECR 映像、隔離資源與日誌保留。查明實際計費項目，不把舊 revision 存在直接等同費用。
- [x] 整理清理清單，保留目前版本、至少一個實測可回復 digest、正式資料與必要 state；刪除前確認沒有服務引用及仍需保留的證據。
- [ ] 清理後重查服務健康、流量與回復映像可用性；費用效果需待帳單反映後才能判定。

**驗收：**至少一個完整帳期的實際費用可追溯，通知實收有本人確認，資源保留／清理理由明確。未觸發通知或未結帳時，分項列待驗，不宣稱全數完成。
